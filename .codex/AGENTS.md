# receipt-manager-app 作業ガイド

## 目的と情報源

レシートを管理し、画像アップロードから家計簿の自動生成へ段階的に拡張するWebアプリです。未実装のロードマップ項目を実装済みと扱わないでください。

- 回答・作業報告は日本語で、変更の目的と結果を簡潔に説明してください。
- 作業開始時に `git status --short` と関連ファイルを確認し、ユーザーの未コミット変更を保持してください。
- READMEは仕様の入口です。ロードマップや構成例に古い記述があるため、実装状況はコード・テスト・設定も確認してください。不一致を見つけた場合は、今回の変更に関係する範囲で整合させてください。
- バージョンは `frontend/package.json`・`package-lock.json`・`backend/go.mod` を確認してください。
- `frontend/` の作業では `frontend/AGENTS.md` の追加指示も読み、該当するNext.jsの同梱ドキュメントを確認してください。

## 実装方針

- 小さな機能単位で変更し、既存の命名・構成・責務分担に合わせてください。依頼と無関係なリファクタリングや依存関係の更新を混ぜないでください。
- 機能追加では、必要なDB変更とAPI契約を整理してからバックエンド、フロントエンドの順に実装してください。不要な層や抽象化を追加する必要はありません。
- Goは変更したファイルに `gofmt` を適用してください。SQLはRepositoryに置き、入力値はプレースホルダーで渡してください。
- 登録・更新の共通入力処理は `bindReceipt()` と `Receipt.Validate()` を活用し、同じ検証を各ハンドラーに重複させないでください。
- TypeScriptのstrict設定を維持し、安易な `any` や型検査の無効化で問題を回避しないでください。`@/` は `frontend/src/` を指します。
- フロントエンドではServer／Client Componentの境界を確認してください。API通信を変更する場合はHTTPエラー、読み込み中、空データの表示も扱ってください。
- 入力フォームはバックエンドの制約と整合させ、ラベルやエラー表示を用意してください。最終的な入力検証はバックエンドでも行ってください。

## 守るべきAPI・データの仕様

詳細は `README.md` のAPI説明と関連テストを参照してください。仕様変更を依頼された場合は、実装・テスト・説明を一緒に更新してください。

- 一覧の0件レスポンスは `null` ではなく `[]` です。
- 更新対象はURLのIDで決めます。本文のIDで別レコードを更新しないでください。同一内容の更新も成功として扱います。
- 削除成功はHTTP 204で本文なしです。不正IDは400、対象なしは404、内部エラーは500として区別します。
- 金額は0〜2,147,483,647円の整数です。小数や負数を暗黙に丸めないでください。
- 購入日はタイムゾーン付き日時を受け取り、DBではDATEとして保存します。変換時に購入日が意図せずずれないか確認してください。
- 店名・カテゴリの必須判定、Unicodeコードポイント単位の文字数制限、メモの省略／null／空白の扱いを維持してください。
- 不正な入力はService・DB処理の前に拒否し、HTTP 400と `{"message":"理由"}` を返してください。内部エラーの詳細や接続情報を利用者向けレスポンスに含めないでください。

## 動作確認

以下はリポジトリルートから実行するコマンドです。変更に関係する確認を実行し、失敗した場合は今回の変更によるものか既存の問題かを切り分けてください。

| 変更対象 | 確認コマンド |
| --- | --- |
| バックエンド | `cd backend && go test ./...` |
| Goの静的検査 | `cd backend && go vet ./...` |
| フロントエンド | `cd frontend && npm run lint` |
| フロントエンドのビルド | `cd frontend && npm run build` |

- 振る舞いを変更した場合は、正常系・異常系・境界値から必要な回帰テストを追加／更新してください。軽微な文書変更のみの場合、アプリのテストやビルドは不要です。
- フロントエンドには現在 `test` スクリプトがありません。存在しないテストコマンドを実行したり、実行済みと報告したりしないでください。UI変更は可能ならブラウザでも確認してください。
- SQL・マイグレーション・永続化に関わるAPI変更では、MySQL統合テストも実行してください。環境を用意できなければ未実施の理由を報告してください。
- MySQL統合テストは `RECEIPT_TEST_MYSQL_DSN` が未設定だとスキップされます。通常の `go test ./...` 成功だけで実DB検証済みと判断しないでください。
- ローカルDBは `docker compose up -d mysql` で起動できます。開発用DSNを環境変数に設定後、`cd backend && go test ./... -count=1` を実行してください。接続例はREADMEを参照してください。
- 統合テストは単一接続の一時テーブルで既存テーブルを隠しています。この仕組みを維持し、接続共有を壊す並列化や `t.Parallel()` を追加しないでください。

## DB・設定ファイルの扱い

- スキーマ変更は `backend/migrations/` に連番のup／downファイルを追加してください。適用済みの履歴を書き換えるより、新しいマイグレーションで変更してください。
- `make migrate-up` は接続先DBのスキーマを変更します。実行前に対象環境とSQLを確認してください。
- `make migrate-down`、`docker compose down -v`、データ削除や履歴の強制上書きは、対象と影響についてユーザーの明示的な許可がある場合に限って実行してください。
- `.env`、`.env.local`、認証情報、実際のレシート画像や個人情報をコミットしたり、ログ・回答へ貼り付けたりしないでください。設定例はダミー値を使ってください。
- `node_modules/`、`.next/`、`backend/tmp/` などの依存物・生成物を直接修正しないでください。
